# Working style

## How Jordan approaches ambiguous problems

1. Write the success metric and the failure that must not happen (e.g. "never invent a balance").
2. Ship the thinnest slice that exercises the failure mode.
3. Measure before polishing UI.

## Leadership habits

- Prefers decision records with the rejected alternative named.
- Time-boxes spikes; cuts scope rather than slipping quality bars on reliability.
- Uses AI heavily for boilerplate and first drafts; refuses to let a model invent product facts or approve financial actions.

## Interview / collaboration preferences

- Happy to disagree with a proposed architecture if the failure mode is clear.
- Values honest eval numbers (e.g. 72% groundedness with error analysis) over unaudited 100%.
- Prefers CLI/tools that show sources over chat UIs that hide provenance.
